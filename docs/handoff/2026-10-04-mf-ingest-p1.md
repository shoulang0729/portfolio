## 1. 背景・ゴール

### 背景（macops 調査・2026-10-04）
- Mac mini の launchd `com.toshio.mf-snapshot`（毎日 05:00 CST = 21:00 UTC 前日）が `scripts/fetch_mf.py run` を実行し、`data/mf-holdings.json` を main へ自動 commit/push、あわせて networth を Worker（`PUT /networth`）へ送る。
- 10/03・10/04 の定時取込が失敗した。10/03 は Chrome 起動時の EAGAIN、10/04 は MF ポートフォリオ画面の `wait_until="networkidle"` が 45 秒でタイムアウト。Mac の再起動と UCSS（プロキシ）の特権ヘルパー入れ替えの後、**同じコードで成功**した。原因は分かっていない。
- **失敗に気づいたのは調査のときだった**。`notify()` は Telegram の環境変数（`TG_BOT_TOKEN`/`TG_CHAT`）が無いと stderr と macOS 通知しか出さない。実際の plist にこの変数があるかは未確認。
- 既存の `.github/workflows/mf-freshness.yml`（#312）は 22:00 UTC（06:00 CST）に動くが、閾値が `STALE_DAYS=3` で、しかも `asOf`（日付のみ。例 `2026-10-04`）を **UTC 0 時**として経過時間を計算している。このため**4 日続けて失敗するまで Issue が立たない**（§3.2 の前後比較を参照）。Issue 本文の手順も旧ルーティン（Claude for Chrome）を指したまま。
- networth の Worker 送信（`push_networth_to_worker`・urllib・`X-Pin-Hash`）は、定時実行の直近 7 回すべて HTTP 403（kvPushed=False）。Worker のコード上、`PUT /networth` が 403 を返す経路は無い（PIN 欠落・不一致は 401、未設定は 428、Origin 無しは通す）。このため Worker に届く前で止められている可能性が高い（Cloudflare エッジの UA ブロック〔error 1010 等〕、UCSS/clash プロキシ、`MF_WORKER_URL` の宛先違い）。**ただし断定はしない**。

### ゴール
- **A**: 403 が「どこで」起きているかを、Mac での curl 調査で特定する。そのうえで、次に失敗したら原因がログと通知から読めるようにする（A1）。必要なら User-Agent を明示して直す。
- **B**: 取込が止まったら、**その日の朝のうちに** Mac の外（GitHub）で気づけるようにする（B1）。一時的な失敗（起動失敗・タイムアウト）はスクリプトの中で自動で再試行して吸収する（B2）。
- 両案件とも、**自動で書き込まれるデータの形（`data/mf-holdings.json` のキー・形状、KV networth の形状）は変えない**。

## 3. 変更手順

### 3.0 調査 A0（macops・Mac mini で実行・コード変更なし）

**目的**: `PUT /networth` の 403 が Worker の手前で起きているかを切り分ける。**PIN もハッシュも送らない**（未認証の PUT は Worker なら 401 で拒否されるので、何も書き込まれない）。

前準備（値は表示しない。キー名だけを見る）:
```sh
# plist にどの環境変数キーがあるか（値は出さない）
plutil -extract EnvironmentVariables xml1 -o - ~/Library/LaunchAgents/com.toshio.mf-snapshot.plist | grep '<key>'
# 実際に使われている送信先（MF_WORKER_URL が plist に無ければ fetch_mf.py の既定値）。ホスト名だけを控える
# プロキシ設定の有無（キー名だけ）
env | grep -i -o '^[a-z_]*proxy[a-z_]*' ; scutil --proxy | grep -E 'Enable|Proxy ' 
export U="<MF_WORKER_URL のオリジン。例 https://<worker>.workers.dev>"
PYUA=$(python3 -c 'import sys;print("Python-urllib/%d.%d"%sys.version_info[:2])')
```

テスト（それぞれステータス行と `server`・`cf-ray`・`cf-mitigated`・`content-type` のヘッダ、本文の先頭 200 文字を控える）:
| # | コマンド | 何を見るか |
|---|---|---|
| T1 | `curl -sS -D - -o ~/nw.body -X PUT "$U/networth" -H 'Content-Type: application/json' --data '{}'; head -c 200 ~/nw.body; rm -f ~/nw.body` | curl の既定 UA。401 なら Worker に届いている |
| T2 | T1 に `-A "$PYUA"` を足す | urllib と同じ UA 文字列だけで 403 になるか |
| T3 | T1 に `-A 'portfolio-mf-snapshot/1'` を足す | 明示 UA で 401 になるか |
| T4 | `python3 - <<'PY'`（urllib.request で PIN 無しの PUT を送り、status・server・cf-ray・本文先頭 200 文字を表示）`PY` | 実運用と同じスタック（TLS 指紋を含む）での結果 |
| T5 | T2 と T4 を UCSS を外して（または該当ホストを DIRECT にして）再実行 | プロキシが原因かどうか |
| T6 | T4 を launchd と同じ環境で 1 回（例: 一時的な plist、または `launchctl asuser`） | 対話シェルと launchd で環境変数・プロキシが違うかどうか |

判定:
| 観測 | 解釈 | 対処（担当） |
|---|---|---|
| 401（JSON 本文） | Worker に届いている。403 は別の条件（例: launchd 環境だけで起きる） | T6 の結果を見て判断。A1 の診断ログで次回を確認 |
| 403・`server: cloudflare`・`cf-ray` あり・本文に `error code: 1010` 等。T2/T4 だけ 403 で T1/T3 は 401 | Cloudflare エッジの UA・ブラウザ判定によるブロック | A1 で UA を明示（PR1）。直らなければ Cloudflare ダッシュボードの Bot/WAF 設定を確認（Toshio） |
| 403・`cf-ray` 無し・`server` が cloudflare 以外。または T5 でだけ 401 | UCSS/clash プロキシが遮断している | 該当ホストを DIRECT にするルール（macops）。コード変更は A1 の診断だけ |
| 404 や想定外のホスト名・別サービスの本文 | `MF_WORKER_URL` の宛先違い | plist の値を直す（macops）。リポにあるものに既定値の誤りがあれば A1 で直す |

- 結果は本 doc の実装ログに**判定の行だけ**を書く（例「T2/T4 のみ 403・cf-ray あり・1010 → UA ブロック」）。URL のクエリ、PIN、ハッシュ、金額は書かない。cf-ray の値も書かない。

### 3.1 PR1（A1）: networth 送信の失敗診断＋User-Agent の明示（`scripts/fetch_mf.py`）

1. `push_networth_to_worker` が送るリクエストに `User-Agent: portfolio-mf-snapshot/1 (+https://github.com/shoulang0729/portfolio)` を付ける。定数はモジュール先頭に 1 か所だけ置く。**MF にアクセスする Playwright 側の UA は変えない**。
2. `urllib.error.HTTPError` を捕まえたら、次の項目を 1 行にまとめてログ（stderr）と `notify()` の両方に出す。
   - `status`（例 403）・`reason`
   - レスポンスヘッダ `server`・`cf-ray`・`cf-mitigated`・`content-type`（あれば）
   - 本文の先頭: 最大 512 バイトを読み、`utf-8`（`errors="replace"`）で復号し、空白をまとめて**160 文字で切る**。`content-type` が HTML のときは `error code: NNNN` と `<title>` だけを抜き出す。
   - 送信先は**ホスト名とパスだけ**（`host/networth`）
3. `urllib.error.URLError`（接続・プロキシ・TLS の失敗）も、例外クラス名と `reason` を同じ形式で出す。
4. **絶対に出さないもの**: リクエストヘッダ（`X-Pin-Hash` を含む）、リクエスト本文（networth の値）、PIN、ハッシュ、URL のクエリ。
5. 挙動は今と同じにする。KV 送信が失敗しても holdings の commit/push は止めない。終了コードも変えない。kvPushed=False の扱いも今のまま。通知は 1 回の実行で 1 回まで。
6. 通知の例（値は合成）:
   - 変更前: （stderr に `HTTP Error 403: Forbidden` 程度。通知されないか、中身が読めない）
   - 変更後: `networth KV 送信失敗: HTTP 403 Forbidden host=<worker-host>/networth server=cloudflare cf-ray=0000000000000000-XXX body="error code: 1010"`
7. テスト（`tests/test_fetch_mf.py`・合成値のみ）: `urlopen` をモックして HTTPError（合成ヘッダ・合成本文）を発生させ、(a) 通知文に status・server・cf-ray が入ること、(b) 合成ハッシュ文字列（例 `SYNTHETIC_PIN_HASH`）と合成金額が通知文とログに**含まれない**こと、(c) 送ったリクエストに上記の User-Agent が付いていること、を確かめる。

**UA をいつ入れるか（推奨）**: **A1 に最初から入れる。ただし A0 の curl 調査はマージ前に済ませる**。
- 理由: UA の明示は副作用がほぼ無い（Worker は UA を見ていない）。Cloudflare の UA ブロックが原因ならこれで直る。原因が別でも、送り手を一意に見分けられる利点が残る。
- A0 を先にやる理由: UA を入れた後で 403 が消えても、A0 が無いと「UA が原因だったのか、たまたま別の要因が消えたのか」が分からなくなる。A0 は Mac で 10 分ほどの作業なので、実装と並行して進められる。
- A0 でプロキシや宛先が原因と分かった場合も UA は残す。その対処（DIRECT ルール・plist 修正）は macops がリポ外で行う。

### 3.2 PR2（B1）: 鮮度の見張りを「当日の取込漏れ」で検知する（`.github/workflows/mf-freshness.yml`）

新しいワークフローは作らず、**既存の `mf-freshness.yml` を直す**（ラベル `stale-mf-holdings` による冪等な起票・更新・自動クローズの仕組みはそのまま使う）。

1. **判定を「CST の当日」と `asOf` の日付差にする**
   - `TODAY=$(TZ=Asia/Shanghai date +%F)`、`LAG=(TODAY − asOf)` を日数で計算する（両方とも日付どうし。`date -d "$X" +%s` を 86400 で割る）。
   - `LAG >= STALE_DAYS` なら起票または更新し、そうでなければ問題なし（既存 Issue があれば自動クローズ）とする。LAG が負（時計のずれ）の場合も問題なしになる。
   - `STALE_DAYS` の既定値は **1**（その日の取込が無ければ当日に起票）。env で変えられる形は残す。
   - 前提の確認（implementer）: `fetch_mf.py` が `asOf` に**実行した日の Mac ローカル日付（CST）**を入れ、データに変化が無い日も毎日 commit していること。もし「変化が無ければ commit しない」実装なら、asOf ではなく最終コミット日時で判定する。最終コミット日時は `gh api "repos/$REPO/commits?path=data/mf-holdings.json&per_page=1" --jq '.[0].commit.committer.date'` で取る（shallow checkout だと `git log` が正しく取れないため）。
2. **前後比較**（05:00 CST の取込が 10/03〜10/05 の 3 日続けて失敗し、`asOf=2026-10-02` のまま、とした例）
   | 時点 | 変更前（22:00 UTC・UTC 0 時起点・閾値 3） | 変更後（00:40 UTC・CST 日付差・閾値 1） |
   |---|---|---|
   | 10/03 朝（1 日目の失敗） | 経過 1 日（10/02 22:00 UTC 判定）→ 起票しない | 08:40 CST 10/03 判定、LAG=1 → **起票** |
   | 10/04 朝（2 日目） | 経過 2 日 → 起票しない | LAG=2 → Issue を更新 |
   | 10/05 朝（3 日目） | 経過 2 日（10/04 22:00 UTC 判定）→ 起票しない | LAG=3 → Issue を更新 |
   | 10/06 朝（4 日目） | 経過 3 日 → ようやく起票 | 復旧していれば LAG=0 → 自動クローズ |
3. **実行時刻**: `cron: '40 0 * * *'`（00:40 UTC = **08:40 CST**）。理由は次のとおり。
   - 05:00 CST の取込に、PR3 の再試行（最悪およそ 10 分）と将来の予備実行（§3.5）が加わっても 3 時間以上の余裕がある。
   - 朝のうちに気づける。
   - 他のバッチの時刻（per-daily 20:15・kv-resync 23:30・weekly 日曜 02:00・fund-holdings 03:00、いずれも UTC）と重ならない。分を `:00` からずらしているので、GitHub の定時実行が混み合う時間帯の遅延も受けにくい。
4. **concurrency**: `portfolio-data-batch` には**入れない**。独立したグループ `mf-freshness`（`cancel-in-progress: false`）を付ける。
   - 理由: このジョブは読み取りと Issue 操作だけで、commit しない。同じグループにすると、GitHub の仕様（同じグループの「待ち」は 1 件だけ残し、古い待ちは取り消す）で、**データバッチの待機中の実行がこのジョブに取り消される**おそれがある。
5. **Issue 本文の更新**: 旧ルーティン（Claude for Chrome）への案内をやめ、次の内容にする。
   - `asOf`、CST の当日、LAG
   - 最終コミット日時（上記の `gh api`）
   - 確認手順: Mac mini の `~/.mf-snapshot/err.log` の末尾を見る → `launchctl kickstart -k gui/$(id -u)/com.toshio.mf-snapshot` で再実行 → `scripts/README-mf-snapshot.md` のトラブルシュート
   - 金額や口座名は本文に入れない（このジョブはそれらを読まない）。
   - タイトルの例: `MF取込が N 日遅れ（asOf YYYY-MM-DD）`
6. **権限**: `permissions: contents: read / issues: write` のままで足りる（`gh issue list/create/edit/close`・`gh label create`・commits API の読み取り）。**GitHub Secrets は追加しない**（`GITHUB_TOKEN` のみ）。GITHUB_TOKEN で作った Issue は他のワークフローを起動しないが、リポを Watch していれば Toshio に GitHub の通知が届く。
7. `asOf` が無い、または日付として読めない場合は、今と同じくジョブを赤にする（`::error::`）。

### 3.3 PR3（B2）: ブラウザ起動〜取得の再試行（`scripts/fetch_mf.py`）

1. **再試行の範囲**: 永続プロファイルでのブラウザ起動 → ページ取得 → `_scrape_all` まで（`with_page` のブロック全体）。**チェックサム検証・ファイル書き込み・git commit/push・KV 送信は範囲の外**（再試行ループの後に 1 回だけ実行する）。
2. **再試行する失敗（一時的なもの）**:
   - ブラウザの起動失敗（Playwright の launch 系の `Error`、`OSError`/`BlockingIOError` の errno EAGAIN、`Target closed`/`browser has been closed` 系）
   - Playwright の `TimeoutError`（`goto`・待ち条件・セレクタ待ち）
3. **再試行しない失敗（その場で今と同じ通知をして中止）**: ログイン切れの判定、チェックサム不一致（口座・総額のずれ）、口座が 1 件も取れない（セレクタ不一致）、設定ファイルの読み込みエラー、その他の想定外の例外。
   - 実装: 一時的な失敗だけを `TransientFetchError`（新設）に包み直し、ループでは**それだけ**を捕まえる。ログイン切れやチェックサムには既存の判定と例外をそのまま使う。
4. **回数と間隔**: 合計 **3 回**（再試行 2 回）、待ちは 30 秒 → 120 秒（定数で 1 か所に置く）。最悪でも 05:00 開始から 10 分程度で終わる。
5. **毎回きれいにやり直す**: 次の試行の前に、前回の context/browser を `finally` で確実に close する。永続プロファイルのロック（`SingletonLock` 等）が残ると、次の起動が必ず失敗するため。close 自体が失敗しても無視して続ける。プロファイルのロックファイルを**消す処理は入れない**（MF のセッションを壊すおそれがある）。
6. **ログと通知**:
   - 各試行の失敗は stderr に 1 行出す（例 `mf-snapshot: attempt 1/3 failed: TimeoutError (networkidle 45000ms) — retry in 30s`）。
   - 再試行のうえで成功した場合は stderr に 1 行だけ出す（`attempt 2/3 succeeded`）。**成功時は通知しない**という既存の方針を守る。
   - 3 回とも失敗したら `notify()` で 1 回通知する。内容は試行回数・最後の例外クラス・短いメッセージで、値は入れない。
   - **データファイルにはこの情報を足さない**（データの形は変えない）。
7. **事前確認用の実行モード**: マージ前に Mac で確かめるため（§4）、`fetch_mf.py` に「取得・検証まではするが `data/` への書き込み・commit/push・KV 送信をしない」モードが要る。**既にあればそれを使う**。無ければ `run --dry-run` を追加する。`--dry-run` を付けないときの挙動は 1 行も変えない。dry-run の出力は件数と検証結果だけにする（金額は出さない）。
8. **テスト**（`tests/test_fetch_mf.py`・Playwright はモック）:
   - (a) 1 回目に TimeoutError、2 回目に成功 → 合計 2 回で成功し、通知しない
   - (b) EAGAIN が 3 回続く → 3 回で打ち切り、通知 1 回
   - (c) ログイン切れ → 1 回で中止し、既存の通知
   - (d) チェックサム不一致 → 再試行しない
   - (e) 各試行の後に close が呼ばれる
   - 待ち時間はモックで 0 にする。
9. **ドキュメント**:
   - `scripts/README-mf-snapshot.md` の「通知が来るのは…だけ」を「ログイン切れ／チェックサム不一致／再試行しても失敗／networth KV 送信失敗」に直す。さらに、実行時刻（05:00 CST）、鮮度の見張り（mf-freshness が 08:40 CST に確認）、Telegram 変数が無いと macOS 通知だけになる注意を追記する。
   - `scripts/com.toshio.mf-snapshot.plist` のテンプレートは時刻を `Hour 5` にし、コメントを「Mac のローカル時刻（CST）」に直す。値は `__set_or_omit__` のまま。

### 3.4 PR4（B3・条件付き）: 待ち条件を `domcontentloaded`＋表の出現待ちに替える

- 内容: L220・L262 付近の `wait_until="networkidle"` を `wait_until="domcontentloaded"` に替え、その後に `page.wait_for_selector(<data/mf-import-config.json の fetch.selectors にある口座表のセレクタ>, timeout=…)` を足す。セレクタはコードに直書きせず、既存の config の値を使う（config の schema は変えない）。
- **PR3 に含めず、別の PR にする（推奨）**。理由は次のとおり。
  1. 10/04 の失敗の原因が networkidle だとは断定できない（同じコードが再起動後に成功している）。
  2. 待ち条件を変えると、DOM を読むタイミングが変わる。描画の途中で読むとチェックサム不一致になり得る。この場合も push はされない（安全な失敗）が、通知が増える。PR3 と分けておけば、Mac 確認でどちらの影響かを切り分けられる。
  3. PR3 の再試行ログ（`attempt n/3 failed: TimeoutError (networkidle …)`）で再発の頻度が見えるようになる。
- **着手する条件（推奨）**: PR3 のマージ後 2 週間のうちに、networkidle のタイムアウトが 2 回以上ログに出る、または再試行しても失敗する日がある場合。そうでなければ見送る。着手するときは別の Issue を立てる（本案件 B の Issue は PR3 で閉じる）。→ **要 Toshio 判断 (3)**

### 3.5 (c) launchd の予備時刻（その日の取込が済んでいればスキップ）: **今回は見送り（推奨）**

- (a) で当日の朝に気づけるようになり、(b) で数分以内に直る一時的な失敗は吸収できる。
- 10/03 のように**再起動するまで直らない**種類の失敗は、数時間後に予備実行しても直らない見込みが高い。
- 予備実行を入れるには「その日の取込が済んでいればスキップする」判定をスクリプトに足す必要がある。足さないと 1 日 2 回 MF にアクセスすることになり、規約上のリスクと不要な commit が増える。
- 判断の材料: PR3 のマージ後 2〜4 週間の再試行ログで、「その日の 05:00 には直らず、数時間後なら直った」例が見つかったら、改めて設計する。その場合は `run --skip-if-fresh` と plist への 2 つ目の `StartCalendarInterval`（plist の変更は macops）を組み合わせる。→ **要 Toshio 判断 (4)**
