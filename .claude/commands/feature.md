portfolio の 設計→実装→レビュー パイプラインを次のお題で回す: $ARGUMENTS

手順（各ステップは対応するサブエージェントに委譲する）:
0. **サイズ判定（PM=親が実施）**: お題が **S**（CLAUDE.md「サイズ判定」の非接触条件をすべて満たす見た目のみの小変更）なら **architect を省略**し、親が受け入れ条件つきの簡潔な Issue を起票して 2 へ。迷ったら M/L としてフルで回す。関連する小さいお題が複数あれば 1 Issue（箇条書き）＋1PR にまとめてよい。
1. **architect** サブエージェントで設計する。機能別の設計ファイル `docs/handoff/YYYY-MM-DD-<slug>.md` を新設し、GitHub Issue を起票。Issue 番号・設計ファイルのパス・Toshio 確認要否を報告させる。投資判断の正本値や資産データの扱いに関わる判断が残る場合はここで停止してユーザーに確認する。
1.5 **モック承認（画面構成・レイアウトの再編を含むお題のみ）**: 実装着手前に、設計書のレイアウト仕様から簡易 HTML モックを1枚作ってユーザーの承認を得る（アプリのコードは触らない）。文言・余白・色などの S レーンでは不要。
2. **implementer** サブエージェントで、その Issue を feature ブランチで実装する。品質ゲートを PASS させ、PR を出す。
3. **reviewer** サブエージェントで PR を検証する。全 PASS かつ load-bearing 逸脱なしなら承認コメント → squash マージ → 公開反映確認。**Toshio 確認対象**ならマージせず `needs-toshio` を付けて報告。FAIL や逸脱があれば implementer に差し戻す。

並列運用（PM の裁量）:
- 互いに独立なお題（触るファイル群が重ならない）は別ブランチで並走してよい。同じファイル群を触るお題、`index.html` の `?v=` bump が必要なお題どうしは直列。
- お題 N の実装/レビュー中に、お題 N+1 の architect を先行起動してよい（設計ファイルは機能別なので衝突しない）。

環境注記: gh CLI が無い環境（クラウドセッション等）では Issue/PR/マージを親が GitHub MCP で代行し、サブエージェントは本文ドラフトをファイルで受け渡し、git は commit まで（push は親）。

停止条件: architect が投資判断・資産データの扱いの決定を要する / reviewer が load-bearing 違反か公開リポ検査の該当を検出 / 品質ゲートが FAIL / マージ前の Mac 実機確認が必要（MF 取得スクリプトのうちログイン・取得処理・公開用の除去処理・自動 commit/push 処理を変える場合のみ。それ以外はマージ後に即時確認＝CLAUDE.md「クラウドから実行できないもの」）。いずれもユーザーに要点を報告して指示を仰ぐ。
